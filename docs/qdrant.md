# Часто задаваемые вопросы: Qdrant

## Векторы

### Какова максимальная размерность вектора, поддерживаемая Qdrant?

Для плотных векторов Qdrant поддерживает до **65 535 измерений**.

### Каков максимальный размер метаданных вектора, который можно хранить?

Жесткого ограничения на размер метаданных нет, однако его следует оптимизировать с учетом производительности и потребления ресурсов. Пользователь может задать верхние ограничения в конфигурации.

### Может ли один и тот же запрос поиска по сходству возвращать разные результаты на разных машинах?

Да. Из-за различий в аппаратной конфигурации и параллельной обработке результаты могут немного отличаться.

### Как выбрать подходящие векторные эмбеддинги для моего случая?

Это зависит от характера ваших данных и конкретного приложения. Следует учитывать такие факторы, как размерность, наличие специализированных для конкретной предметной области моделей и характеристики производительности различных эмбеддингов.

### Как Qdrant работает с разными векторными эмбеддингами от разных провайдеров в одной коллекции?

Qdrant поддерживает несколько векторов для одной точки данных, поэтому разные эмбеддинги от различных провайдеров могут сосуществовать в одной коллекции.

### Можно ли перенести мои эмбеддинги из другого векторного хранилища в Qdrant?

Да. Qdrant поддерживает миграцию эмбеддингов из других векторных хранилищ, что упрощает переход и использование возможностей Qdrant.

### Почему количество индексированных векторов не совпадает с количеством векторов в коллекции?

Qdrant не всегда должен индексировать все векторы в коллекции.

Данные хранятся в сегментах, и если сегмент достаточно маленький, эффективнее выполнить полный перебор по нему.

Убедитесь, что статус коллекции находится в состоянии `green`, а количество неиндексированных векторов меньше порога индексации.

### Почему информация о коллекции показывает неточное количество точек?

Collection Info API в Qdrant возвращает приблизительное количество точек в коллекции.

Если вам нужно точное количество, можно использовать API `count`.

### Векторы в коллекции не совпадают с теми, которые я загрузил.

Есть две возможные причины:

- Вы использовали метрику расстояния `Cosine` в настройках коллекции. В этом случае Qdrant предварительно нормализует ваши векторы для более быстрого вычисления расстояния. Если вам необходимо сохранить исходные векторы без изменений, рассмотрите использование метрики `Dot`.
- Вы использовали тип данных `uint8` для хранения векторов. `uint8` требует специального формата входных значений, который может быть несовместим с типичным результатом моделей эмбеддингов.

### Сколько векторов можно хранить в одной точке? Может ли точка вообще не иметь вектора?

Точка может содержать любое количество именованных векторных полей — плотных, разреженных и multivector. При этом каждое поле должно быть настроено в схеме коллекции.

Жесткого ограничения на количество именованных векторных полей для одной точки нет. Однако существуют практические ограничения: каждый дополнительный вектор увеличивает потребление памяти, поэтому реальный предел определяется доступными RAM и дисковым пространством.

Можно добавить один вектор или несколько векторов с разными именами. Например, плотный вектор для семантического поиска и разреженный вектор для поиска по ключевым словам. Это позволяет выполнять гибридные запросы над несколькими представлениями одних и тех же данных внутри одной коллекции.

Для одного multivector-поля существует жесткое ограничение: общее количество элементов типа `float` после преобразования в плоский массив должно быть меньше **1 048 576**.

На практике:

`количество_sub-векторов × размерность_вектора < 1 048 576`

Для модели с размерностью 4096 это ограничивает один multivector максимум примерно **255 sub-векторами**.

Это ограничение нельзя изменить. Если модель с late interaction создает больше sub-векторов, чем позволяет лимит, рекомендуется объединять token-векторы перед сохранением либо разделять документ на несколько точек и агрегировать оценки во время запроса.

Точка также может иметь **ноль векторов**. Если при upsert не передать ни одного вектора, Qdrant сохранит точку только с ее ID и payload.

Это полезно, если вы хотите использовать Qdrant как хранилище документов с фильтрацией или планируете добавить вектор позже.

Точка без вектора не появится в результатах поиска ближайших соседей, но будет полностью доступна через `scroll` и фильтрацию по payload.

### Может ли Qdrant самостоятельно генерировать векторные эмбеддинги?

Да. Если вы используете Qdrant Cloud, можно генерировать эмбеддинги с помощью Qdrant Cloud Inference. Это позволяет за один API-вызов выполнить эмбеддинг, сохранение и индексацию данных, поэтому отдельный inference-сервис или pipeline для эмбеддингов не требуется.

Cloud Inference поддерживает плотные модели для семантического поиска, разреженные модели для поиска по ключевым словам, а также мультимодальные модели для поиска по изображениям и тексту.

Поскольку эмбеддинги генерируются внутри сети вашего кластера, не возникает накладных расходов на внешние API — это означает меньшую задержку, отсутствие затрат на исходящий трафик и меньшее количество компонентов системы.

Некоторые модели доступны бесплатно на всех уровнях кластеров, включая бесплатный уровень. Доступные модели и текущее использование можно посмотреть на вкладке **Inference** страницы информации о кластере в Qdrant Cloud Console.

Если вы используете Qdrant с открытым исходным кодом или самостоятельно развернутый Qdrant, Cloud Inference недоступен. Можно использовать FastEmbed — легковесную локальную библиотеку инференса Qdrant — либо собственную модель или сервис для генерации эмбеддингов.

### Должен ли каждый chunk документа быть отдельной точкой в Qdrant?

Да. В большинстве RAG-систем каждый chunk хранится как отдельная точка.

Текст chunk'а (или ссылка на него) помещается в payload, а его embedding — в вектор. Точки могут иметь общее поле `document_id` в payload, чтобы можно было определить исходный документ.

Способ разбиения документа на chunks существенно влияет на качество поиска и зависит от предметной области.

В качестве отправной точки:

- разбиение по абзацам хорошо работает для книг и обычного текста;
- разбиение по предложениям обычно лучше подходит для технических статей и Q&A-контента.

Стоит экспериментировать: стратегия chunking является одной из наиболее важных переменных, влияющих на качество retrieval.

### Как внутри Qdrant работает удаление точки? Перестраивается ли индекс после каждого удаления?

Qdrant реализует удаление как **мягкое удаление (soft delete)** с использованием битовой маски, поэтому индекс не перестраивается после каждого удаления.

Битовая маска — легковесная структура данных, позволяющая Qdrant быстро определить, нужно ли исключить точку из операции, не обращаясь к данным удаленной точки.

Физическая очистка выполняется в фоновом режиме оптимизатором Vacuum Optimizer.

После операции удаления точка сразу становится недоступной через API. Механизм soft delete является внутренней деталью реализации.

### Вызывает ли upsert точки без изменений удаление и повторную вставку?

Да. Перед выполнением upsert Qdrant не проверяет сходство данных.

Если выполнить upsert для уже существующей точки с абсолютно идентичными данными, система все равно пометит старую версию как удаленную и вставит новую копию.

### Что означает поле `version` у точки?

Поле `version` в ответе Query API представляет собой внутренний номер операции на уровне shard для последнего изменения точки.

Он увеличивается внутренними процессами, поэтому не является надежным показателем количества записей на уровне приложения и не может сравниваться между репликами.

Если вам необходимо отслеживать количество изменений на уровне приложения, используйте счетчик в payload, управляемый самим приложением.

## Поиск

### Как Qdrant обрабатывает обновление данных и поиск в реальном времени?

Qdrant поддерживает обновление векторных данных в реальном времени. Только что добавленные, измененные и удаленные векторы становятся доступны для поиска сразу.

Во время фонового обновления индекса система использует полный перебор для поиска по неиндексированным сегментам.

### В результатах поиска я вижу векторы со значением `null`. Почему?

По умолчанию Qdrant старается минимизировать сетевой трафик и не возвращает векторы в результатах поиска.

Однако можно принудительно включить их возврат, установив параметр `with_vector` для Search/Scroll в значение `true`.

Если после этого в результатах по-прежнему появляется `"vector": null`, возможно, передаваемый вектор имеет неправильный формат либо существует проблема с тем, как вызывается метод upsert.

### Как выполнить поиск без вектора?

Вероятно, вам нужен метод `scroll`.

Он позволяет получать записи по фильтрам или даже последовательно перебрать все записи коллекции.

### Мой поиск по векторам с фильтрацией работает медленно. Что проверить в первую очередь?

Добавьте **payload index** для всех полей, по которым выполняется фильтрация.

Индексация payload часто дает больший прирост производительности для фильтрованных запросов, чем другие оптимизации, например изменение параметров HNSW.

Для наилучшего результата создавайте payload-индексы **до загрузки данных**.

Если данные уже загружены, можно перестроить HNSW-индекс, внеся минимальное изменение в `m` или `ef_construct`, например изменив значение со 100 на 101.

Пока новый индекс строится, запросы продолжают обслуживаться старым индексом, поэтому простоя нет.

Не следует сразу возвращать `ef_construct` к исходному значению — оставьте новое значение.

Чтобы запретить клиентам фильтровать по полям payload, для которых нет payload index, включите strict mode и установите `unindexed_filtering_retrieve` в `false`.

### Поддерживает ли Qdrant полнотекстовый или гибридный поиск?

Qdrant прежде всего является поисковой системой по векторам. Полнотекстовые возможности реализованы только в той мере, в которой они не ухудшают возможности векторного поиска — как с точки зрения интерфейса, так и производительности.

Qdrant умеет:

- выполнять поиск с полнотекстовыми фильтрами;
- применять полнотекстовые фильтры к векторному поиску, то есть выполнять векторный поиск среди записей, содержащих определенные слова или фразы;
- выполнять prefix search и семантический `search-as-you-type`;
- работать с разреженными векторами, например используемыми SPLADE и похожими моделями;
- работать с multivector, например ColBERT и другими late-interaction моделями;
- комбинировать несколько поисковых запросов.

Qdrant не планирует поддерживать:

- retrieval или ranking-функции, не основанные на векторах;
- встроенные онтологии или графы знаний;
- query-анализаторы и другие NLP-инструменты.

Разумеется, Qdrant можно комбинировать с любым специализированным инструментом, который вам нужен, включая полнотекстовые поисковые системы.

### Когда использовать Reciprocal Rank Fusion (RRF), а когда Distribution-Based Score Fusion (DBSF) для гибридного поиска?

Оба метода объединяют оценки нескольких retrieval-веток, например dense и sparse, но работают по-разному.

**RRF (Reciprocal Rank Fusion)** объединяет ранжированные списки на основе позиции результата, а не величины score.

Он хорошо работает, когда оценки разных методов находятся в несовместимых шкалах, что часто бывает у dense и sparse поиска. В качестве начальной стратегии рекомендуется использовать RRF. При необходимости можно настроить веса и параметр `k`.

**DBSF (Distribution-Based Score Fusion)** нормализует оценки на основе их статистического распределения для каждого prefetch перед объединением.

Он может давать лучшие результаты, когда распределения оценок имеют подходящий вид и необходимо, чтобы абсолютные значения score влияли на итоговое ранжирование.

Для собственной стратегии объединения можно использовать Formula Query. Например, можно применять функции затухания для нормализации обеих оценок в диапазон 0–1, а затем объединять их.

Для этого необходимо определить приблизительное распределение оценок для каждого корпуса, поскольку параметры функции затухания нельзя задавать динамически.

Formula Query не поддерживает собственное rank-based fusion, поскольку не имеет доступа к рангам prefetch и работает только с исходными score.

Чтобы определить, какой метод лучше подходит для вашего случая, создайте небольшой набор эталонных запросов и сравните метрики качества retrieval, например **NDCG@10**, для каждого метода.

### Результаты моего гибридного поиска нерелевантны. С чего начать отладку?

Проверяйте следующие пункты по порядку:

1. **Проверьте preprocessing sparse-векторов.** Плохие sparse-результаты часто связаны с токенизацией. Для неанглийского текста настройте stemming и списки стоп-слов с учетом языка.
2. **Изолируйте отдельные ветки.** Выполните dense-only и sparse-only запросы отдельно. Если одна из веток уже сама по себе возвращает плохие результаты, сначала исправьте ее, а уже затем настраивайте fusion.
3. **Настройте веса fusion.** Если обе ветки по отдельности выглядят хорошо, но после объединения качество ухудшается, попробуйте изменить веса отдельных prefetch в конфигурации RRF. Универсального значения по умолчанию нет. Оценивайте результаты на небольшом размеченном наборе запросов.
4. **Добавьте reranking.** Если точность важнее задержки, reranking в качестве финального этапа может исправить ошибки retrieval.

### Какие существуют три подхода к фильтрации в Qdrant и когда следует использовать каждый?

Существует три стратегии:

1. **Только payload index** — логическое разделение данных с помощью фильтрации. Работает при любой cardinality.
2. **Payload index с `is_tenant=true`** — логическое разделение плюс физическое размещение данных одного tenant вместе на общих shards с отдельными подиндексами для каждого tenant. Также работает при любой cardinality. Однако только одно поле коллекции может использовать эту настройку.
3. **Custom sharding (`shard_key_selector`)** — жесткие физические границы с отдельными shards. Устраняет проблему noisy neighbors. Рекомендуется только для низкой cardinality — менее примерно 1000 уникальных значений — и только если вы **всегда** фильтруете по этому полю.

### Если выполнить один и тот же запрос с `limit=20` и `limit=100`, гарантированно ли первые 20 результатов будут одинаковыми?

В целом ожидается, что результаты в пересекающейся части будут согласованными.

Однако HNSW является приближенным алгоритмом. Более высокий `limit` увеличивает область поиска и может найти точки, которые лучше соответствуют запросу, чем точки, найденные при меньшем `limit`.

Если при `limit=100` будут найдены более подходящие точки, порядок первых 20 результатов может измениться.

### Что означает поле `time` в ответе Query API? Включает ли оно сетевую задержку?

Значение `time` указывается в секундах и представляет общее время, которое сервер Qdrant потратил на обработку запроса.

Сетевое время между клиентом и сервером в это значение не входит.

### Почему при пагинации результатов поиска я получаю дубликаты?

Поскольку HNSW является приближенным алгоритмом, порядок результатов может немного меняться между запросами.

В результате пагинация с использованием `offset` может вернуть одну и ту же точку на нескольких страницах или пропустить некоторые точки.

Это ожидаемое поведение, а не ошибка.

Есть три способа решить проблему:

- **Пагинация на стороне клиента** — получить большой набор результатов одним запросом, например первые 100 результатов, а затем разбивать его на страницы на стороне клиента. Это исключает дубликаты и уменьшает количество round-trip запросов, но требует передачи большего количества данных, чем пользователь видит одновременно.
- **Точный поиск** — использовать exact search, который обходится без HNSW и сканирует все векторы, возвращая результаты в стабильном детерминированном порядке. Это обеспечивает корректную работу пагинации с `offset`, но практически применимо только к небольшим коллекциям из-за большей задержки.
- **Исключать уже просмотренные ID** — для каждой следующей страницы передавать фильтр `must_not: has_id`, содержащий ID точек с предыдущих страниц. Список исключений увеличивается на `limit` элементов с каждой страницей, поэтому этот подход хорошо подходит для последовательной пагинации вперед, но непрактичен для перехода сразу на произвольную страницу.

### Если `limit` выше `hnsw_ef`, увеличивает ли Qdrant `hnsw_ef` автоматически?

Да. Внутри Qdrant устанавливает:

`ef = max(ef, limit)`

Таким образом, список кандидатов всегда как минимум равен количеству запрашиваемых результатов.

### Каково значение `hnsw_ef` по умолчанию во время поиска?

По умолчанию `hnsw_ef` равен `ef_construct`, значение которого по умолчанию составляет **100**.

`ef_construct` — конфигурация уровня коллекции, определяющая количество соседей, рассматриваемых при построении графа.

`hnsw_ef` — параметр конкретного запроса, определяющий размер динамического списка кандидатов во время поиска.

### Каковы значения `rescore` по умолчанию для разных методов квантования?

По умолчанию повторный расчет оценок (`rescore`) включен только для четырех методов квантования:

- binary quantization;
- TurboQuant 1 Bit;
- TurboQuant 1.5 Bit;
- TurboQuant 2 Bit.

Для остальных методов квантования rescoring по умолчанию не выполняется.

Поведение по умолчанию можно изменить с помощью параметра `rescore` во время запроса.

### Что делает `ignore=true` в параметрах поиска с квантованием?

Когда `ignore` имеет значение `true`, Qdrant продолжает обход графа HNSW, построенного на квантованных векторах, но использует точные расстояния полной точности для оценки кандидатов во время обхода вместо квантованных расстояний.

Это может повысить recall, но требует определенных дополнительных затрат, поскольку выбранные соседи могут отличаться от тех, которые были бы выбраны при полностью квантованном поиске.

## Коллекции

### Сколько коллекций можно создать?

Столько, сколько необходимо, однако каждая коллекция требует дополнительных ресурсов.

Настоятельно рекомендуется не создавать множество маленьких коллекций, поскольку это приводит к значительным накладным расходам по ресурсам.

Создание отдельной коллекции для каждого пользователя, диалога или документа считается антипаттерном.

### Следует ли использовать именованные векторы или отдельные коллекции для разных embedding-моделей?

Используйте **именованные векторы**, когда данные, для которых создаются embeddings, имеют одинаковую структуру payload и вы хотите выполнять запросы к нескольким векторным пространствам в рамках одного запроса.

Например, можно объединить dense-вектор текста и CLIP-вектор изображения для одного товара.

Используйте **отдельные коллекции**, если:

- схемы payload существенно различаются;
- требуется независимое масштабирование;
- на точке устанавливается и запрашивается только один из настроенных векторов;
- вы тестируете новые embeddings;
- один набор векторов запрашивается значительно чаще другого.

Общее правило: именованные векторы разделяют одну точку и ее payload. Если разные embeddings представляют принципиально разные сущности, они должны находиться в разных коллекциях.

### Можно ли перейти на другую embedding-модель без пересоздания коллекции?

Да, если используются именованные векторы:

1. Добавьте новый именованный вектор для новой модели.
2. Выполните повторную генерацию embeddings для точек в фоновом режиме.
3. Когда будете готовы, удалите старый именованный вектор.

Если именованные векторы не используются, потребуется создать новую коллекцию.

Для миграции без простоя можно использовать смену alias:

1. Создайте новую коллекцию и загрузите данные с embeddings, созданными новой моделью.
2. После завершения индексации атомарно измените alias коллекции так, чтобы он указывал на новую коллекцию.
3. Удалите старую коллекцию после того, как убедитесь в стабильности миграции.

### Почему моя коллекция находится в статусе `grey`?

Статус `grey` означает, что оптимизатор остановился.

Это может произойти, если экземпляр Qdrant был перезапущен во время выполнения оптимизации.

В таком состоянии объем неиндексированных данных может увеличиваться. Поскольку Qdrant использует полный перебор для поиска по неиндексированным сегментам, это ухудшает задержку запросов.

Если включены `indexed_only` или `prevent_unoptimized`, Qdrant не возвращает неиндексированные данные, поэтому результаты поиска могут быть неполными.

Распространенные способы восстановления:

1. Использовать кнопку **Trigger Optimizers** в веб-интерфейсе Qdrant. Она отображается рядом со статусом `grey` на странице информации о коллекции.
2. Отправить любую операцию обновления коллекции, чтобы повторно запустить оптимизацию.

### Почему мои записи отклоняются с HTTP 507?

Запись считается успешно выполненной после того, как как минимум `write_consistency_factor` реплик ее приняли.

Когда для узлов настроены resource quotas, может оказаться, что ни один узел с нужной репликой не может принять запись.

Ошибка 507 означает, что осталось слишком мало реплик для достижения `write_consistency_factor`.

При значении по умолчанию 1 это означает, что ни одна реплика shard не имела свободного места.

Используйте `GET /quotas`, чтобы определить, какой peer заполнен.

Обратите внимание: узел не возобновляет прием записей сразу после снижения использования ресурсов. Сработавший лимит снимается только после того, как использование опустится ниже release margin, который по умолчанию составляет пять процентных пунктов.

### Как загрузить большое количество векторов в коллекцию Qdrant?

Используйте рекомендации из руководства по массовой загрузке данных.

### Какой размер batch рекомендуется для загрузки векторов?

Универсального рекомендуемого размера batch нет.

Оптимальный размер зависит от:

- размерности векторов;
- размера payload;
- конфигурации кластера;
- доступной памяти.

Следует протестировать различные размеры batch на вашей собственной конфигурации.

Хорошая отправная точка — **64–256 точек на batch**.

Однако если операции внутри batch сами по себе дорогие, например обновления затрагивают большое количество точек или выполняются по фильтру, эффективнее отправлять отдельные запросы.

### Можно ли хранить только квантованные векторы и удалить векторы полной точности?

Нет. Qdrant требует векторы полной точности для таких операций, как перестроение индекса, rescoring и других операций.

### Можно ли удалить исходные векторы полной точности после включения квантования?

Нет.

Qdrant требует исходные векторы полной точности, чтобы повторно вычислять квантованные представления при перестроении сегмента Vacuum Optimizer.

Qdrant получает статистику для квантования — `offset` и `alpha` — из векторов полной точности каждого сегмента. Поэтому их удаление сделало бы повторную индексацию невозможной.

## Совместимость

### Совместим ли Qdrant с CPU и GPU для вычисления векторов?

Qdrant в основном использует ускорение на CPU для масштабируемости и эффективности.

Однако также поддерживается GPU-ускоренная индексация на всех основных производителей GPU.

### Гарантируете ли вы совместимость между версиями?

Если ваша версия устарела, совместимость гарантируется только между двумя последовательными minor-версиями.

Это также относится к версиям клиента.

Следите за тем, чтобы версия клиента отличалась от версии кластера не более чем на одну minor-версию.

Qdrant оказывает помощь в устранении проблем и ошибок, специфичных для своих продуктов, однако не отвечает за проверку, написание, переписывание или отладку пользовательского кода.

### Поддерживается ли откат на более старую версию?

Нет. Qdrant не поддерживает downgrade кластера ни в одном из своих продуктов.

При развертывании новой версии Qdrant данные автоматически мигрируют в новый формат хранения.

Эта миграция необратима.

### Как избежать проблем при обновлении до последней версии?

Qdrant гарантирует совместимость только при переходе между последовательными версиями.

Версии необходимо обновлять по одной:

`1.1 → 1.2 → 1.3 → 1.4`

### Следует ли создавать payload indexes до или после загрузки данных?

Создавайте payload indexes **до загрузки данных**, чтобы избежать перестроения индекса.

Однако бывают ситуации, когда создание индексов после загрузки допустимо. Например, можно добавить новую логику фильтрации уже после запуска системы.

Если вы заранее знаете, какие фильтры будете использовать, всегда создавайте индексы до загрузки данных.

Если впоследствии потребуется добавить индекс для другого payload, это также возможно, но следует учитывать снижение производительности во время построения индекса.

### Если мне нужно добавить payload index после того, как HNSW уже построен, как запустить полную повторную индексацию?

Изменение `m` или `ef_construct` автоматически запускает полное фоновое перестроение HNSW.

Если нужно только добавить payload index, внесите минимальное изменение в `ef_construct`, например измените его со 100 на 101.

Пока новый индекс строится, запросы продолжают обслуживаться старым индексом, поэтому простоя нет.

Не следует сразу возвращать `ef_construct` к исходному значению — оставьте новое значение.

### Следует ли создавать отдельную коллекцию Qdrant для каждого пользователя?

Нет. Создание отдельной коллекции для каждого пользователя требует больше ресурсов.

Вместо этого рекомендуется создать **одну коллекцию** и разделять доступ с помощью payload.

Каждая точка Qdrant может иметь payload с метаданными. Для multitenancy можно добавить `user_id` или `tenant_id` для каждой точки.

Чтобы дополнительно оптимизировать хранение, можно включить tenant indexing для полей payload.

## Безопасность

### Безопасен ли кластер Qdrant по умолчанию?

Это зависит от способа развертывания.

Кластеры Qdrant Cloud по умолчанию защищены.

Самостоятельно развернутые экземпляры по умолчанию не защищены: они открыты для всех сетевых интерфейсов и не имеют настроенной аутентификации, пока вы ее не включите.

### Поддерживается ли доступ только для чтения?

Да.

Можно настроить API-ключ только для чтения, который разрешает выполнять запросы, но блокирует все операции записи.

Оба ключа могут быть активны одновременно, поэтому потребителям можно выдать read-only ключ, не меняя основной ключ.

### Можно ли ограничить доступ к определенным коллекциям?

Да.

Qdrant поддерживает контроль доступа на основе JWT, позволяющий выдавать подписанные токены, ограниченные конкретными коллекциями и правами на чтение или запись.

Это полезно для multitenant-развертываний, где каждый пользователь или сервис должен иметь доступ только к собственным данным.

## Cloud

### Можно ли уменьшить масштаб Qdrant Cloud кластера?

Да. Qdrant Cloud позволяет уменьшать масштаб кластера как вертикально, так и горизонтально.

Обратите внимание: при вертикальном уменьшении размера кластера размер диска уменьшить нельзя.
